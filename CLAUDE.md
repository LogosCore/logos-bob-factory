# CLAUDE.md

BOB (`github.com/logoscore/logos-bob-factory`): a bare Logos factory (the module type that builds minions). `cmd/bob-factory/main.go` runs factory-core's `factory.Run` as module_name `bob`, with its own management and the live log tail (module-core `logging.New` teed into a `logstream.Hub`). `build.go` holds its build schema (`schema_version` "3", version 3, two targets: `linux-elf` on `linux/amd64` / `linux/386`, and `windows-exe` on `windows/amd64` / `windows/386` / `windows/arm64`, the same minion compiled for each, which prints its JSON description when run with `describe`; one field of each build field type; HTTP (connection schema v3) with connection parameters per kind: `reverse-call` `method` and `path_prefix`, `reverse-persistent` `path_prefix` only; commands of each kind: required, default, operator-picked), its plan (`Steps`: check the badge when there is one, compile, upload), with the compiler's stdout and stderr streamed into the build log (`lineLog`), and the builder, which reports those steps, compiles the minion (`minion/`, a Go module of its own, copied per build with the description written in as `minion.json`; `compile.go`) for the build's platform (`compiledTargets`), and uploads the binary as `bob-<id8>.bin` (`application/x-executable`) or `bob-<id8>.exe` (`application/vnd.microsoft.portable-executable`) (`artifactKinds`). What differs by OS lives in files of their own, Unix and Windows: the shell (`shell_unix.go`: `/bin/sh -c` in its own process group; `shell_windows.go`: `cmd.exe /d /s /c` as typed, `taskkill /T /F` on a cancel), the machine id (`machine_unix.go`: a container's id, the machine-id; `machine_windows.go`: the SMBIOS UUID via `GetSystemFirmwareTable`, the registry's `MachineGuid`), the hello's integrity and domain (`host_unix.go`, `host_windows.go`: the token's mandatory label, `NetGetJoinInformation`), listings' hidden files (the hidden attribute on Windows), and the `volumes` command (op 13, action `list_volumes`, result `volumes`, picked by default: `volumes_linux.go` reads `/proc/self/mountinfo`, `volumes_windows.go` the drives A: to Z:; `volumes.go` sends them in parts of half a message each); only `syscall`, no new modules. What is plain code (`smbios.go`, `integrity.go`, `shell.go`'s `cmdLine`) is tested on any host (`windows_test.go`); nothing here runs Windows, so vet and lint the minion with `GOOS=windows` (amd64 and 386) too. The image warms the standard library for `linux/amd64`, `linux/386` and `windows/amd64`. Run, the minion stages with core through its first http connection, says hello (a session opens, the hello saying its `max_tasks`), then checks in every `checkin_interval` ± `checkin_jitter` % of its connection until stopped, and logs each step. BOB declares `max_tasks`: the build's limit (default 5, `description.max_tasks`) is how many tasks the minion runs at once, each in a goroutine of its own; its `get_tasks` asks for the room the limit leaves through a call (none when full) and for the limit itself on a persistent connection (a standing allowance); core's `max_tasks` item (17) changes it live and the minion says it back in its next message (`minion/tasks.go`); `exit` cancels the tasks running beside it and waits for their ends (`exitWait`, 10s) before its own. Feedback (protocol item 18, `minion/feedback.go`): a process-wide queue anything reports into (`report`), at most 100 unsent (then a `feedback_dropped` warning), the same one folded into a count, sent first in each message (half its room at most) and at once (the session's runner's nudge); a failed message sends it again. It reports check-ins failing two or more in a row once one works (`failStreak`, `checkin_failed`), the WebSocket closing when the minion did not close it (`ws_closed`), the TCP listener refusing past `max_connections` (`tcp_refused`), a persisted session not given (`session_not_claimed`), and a command that panics (`task_panic`: recovered, the task fails; tests swap commands through `runner.exec`). The `feedback` command (op 14: `level` warning or error, `message`) sends the operator's words. It keeps its session through failed check-ins and starts over from the stage only on a sealed `session_closed`, after 24 hours of failures (`backstop`), or when the stage or hello fails. BOB declares `persisted_sessions`: a build with a `session_id` writes it into the description, and the minion claims it in its hello until a `session_replaced` (then it stops claiming) (`minion/main.go`; `describe` prints the description); its modules (the protocol package, the CBOR library, coder/websocket) are not vendored: the compile uses `-mod=readonly` and the module cache, which the image warms (`go mod download` on a copy without `replace` lines), and fetches what is missing through `GOPROXY` as BOB's environment sets it (a mirror where there is no internet), checked by `minion/go.sum`. While the minion needs an unreleased protocol, `minion/go.mod` has a `replace` to the checkout's absolute path (a build copies the minion to a scratch folder, so a relative one would not resolve), and the git-excluded `docker-compose.override.yml` mounts the checkout at that path; drop it at release. Commands and their params are numbered (`op`, `num`): tasks name them by number, so the minion dispatches on the constants in `minion/ops.go` and carries no command names; `cmd/bob-factory/ops_test.go` checks the schema and `ops.go` agree. A connection of kind `reverse-persistent` (BOB declares `reverse-call` first, then it) keeps a WebSocket to the HTTP channel (`minion/ws.go`): every exchange goes over it, core pushes tasks and cancels within the minion's `get_tasks` allowance, the minion checks in at once after hello (and after each reconnect) and then not on a schedule while the WebSocket stays open (only what it has to send, a pushed task's ack at once, and a failed exchange's retry after the reconnect back-off, 1s doubling up to `ws_reconnect_backoff`; it pings the channel every 30s, `wsPing`, to find a dead link), and a WebSocket that closes reopens after 1s doubling up to `ws_reconnect_backoff`. The HTTP channel closes the WebSocket when its socket to core closes, which is what makes the schedule unnecessary. A connection through the TCP channel (`tcp`, kind `bind-persistent`) makes the minion listen instead (`minion/tcp.go`, `tcpLink`: `listen_port`, `listen_address`, `max_connections`, `keepalive`): the channel dials it when core opens the target's connection, frames are `[len u32 BE][id 16][sealed]`, the newest connection in is the one used, an exchange waits for a dial while none is in. It is the one in use at start only when it comes first in the build; otherwise `switch` to it opens its port (`transport.listen`) and the session goes on through the connection in use, the task saying it listens (an early part: core's cue to dial the session's target), and the move goes through core's dial once it comes (`awaitDial` in `main.go`); no dial in `listenWait` (10m) closes the port and fails the switch. Moving off it is a switch like any (the port closes: `tcpLink.close` stops listening, also when a session ends), and a `for` back onto it waits for a dial the same way. The WebSocket and the listener share the `persistentLink` interface (`transport.link`). BOB declares `failover`: the build's failover policy goes into the description (`failover`, defaults when core sends none), and `minion/failover.go` acts on it in the session loop: `fail_after` failed exchanges in a row (a connection's own `fail_after` overrides it) over at least `fail_for` move the minion to the next connection it may use (`auto`), round the list with `wrap`; a round back to the connection in use pauses `cycle_pause` there; away from its first connection by failover it tries that one again after `failback_after`; an operator's switch resets it. Moves go through `move`, as a switch's, with a `conn_update` saying why. Failover passes listening connections by. Tunnels (protocol items 21 to 26, `minion/tunnel.go`): the `socks` command (op 15, action `tunnel`, operator-picked: `port`, `timeout`, `max_streams`) makes its tunnel as the task is taken (before its ack goes: core opens streams only once it has it) and runs until core cancels it (then its streams close and it ends ok, as with the session's end). Each `tunnel` item is a TCP connect from the host within `timeout` (`dialResult` says why one failed, by the host's errors: `tunnel_unix.go`, `tunnel_windows.go`'s Winsock codes); its reply says the socket's address. Each stream mirrors core's: offsets each way, the eof one place past the bytes, a 256 KiB window the minion gives, at most 1 MiB read ahead of core's ack, unacked data sent again from the ack after `tunnelResend` (5s), a window shut that long probed with one byte, core's data that comes ahead kept until the gap fills; in a message, closes, replies, acks, then data a stream's item in turn (192 items at most, half the room while a file goes). `pending` counts tunnel items, so the minion checks in at once with them; core's `poll` of 0 means at once (`polled`), and a resend due wakes the loop even over a persistent connection (`pollEvery`). Core's items the minion does not take get `unknown_item` (`resume` among them: it keeps its own state); a `rehello` gets a `hello` in the next message, through the connection in use; a `reack` (item 19: which tasks it still has, asked after a claim and over each new listening connection) gets an `ack` naming those it has (running, or ended with an end not yet delivered) and `unknown_task` for each other (`runner.reack`). A held stream is not polled on a guess: core's `poll` item (in a sync-call reply, while the stream's downloader or uploader is there) says how soon to check in, for the next wait only; over a WebSocket or a TCP connection core pushes instead. Each message keeps within the connection in use's `max_message` (`BuildConnection.MessageLimit`, set into the runner each loop): output, data, chunks and listing pieces take two thirds of it at most (512 KiB over the protocol's limit), and a listing piece half of that. The minion holds all of the build's connections (`minion/conns.go`, `transport`) and uses one at a time, the first it can use (an http one of a reverse kind) at start; its hello says which (`conn`, its place from 1). The `switch` command (op 12, action `switch_connection`: `conn`, and `for`, default `0s`) asks the session loop to move: it checks in through the new connection with a `conn_update` and the check-in's items, and moves only if that answers (the task fails, staying put, otherwise); with `for` it moves back when the time is up ("back after …"). The session, keys and schedule stay the same across moves. `stage_test.go` runs a compiled minion against a fake channel and core (stage, hello, a check-in that gets a 404 and keeps the session, one that gets `session_closed` and stages again, then kills it; and one built with a persisted session claiming it, then not after `session_replaced`). The image keeps the Go toolchain (`golang:1.25-alpine`) and the sources in `/app/minion` (`MINION_SRC`); the compile tests use `../../minion` and need `go` on `PATH`. `go test ./...` at the root does not cover `minion/`: vet it in its own directory. `icon.go` holds its icons (constant SVGs sent at registration: `icon`, the lit skin, for dark themes, and `iconLight`, the outline, lines and shading, for light ones; a test checks both against `protocol.ValidateIcon`). `management.go` is BOB's own manifest: `fail_builds` and `log_level` (live), and the `say_hello` action; factory-core adds the builds section (`max_concurrent_builds`, `drain`/`resume`, build counters) next to it, so BOB's manifest cannot use those keys.

Factory plumbing (build requests, progress, results, files, artifacts) stays in `logos-golang-factory-core`; module plumbing in `logos-golang-module-core`. BOB only declares what it builds and builds it.

Build and test: `go build ./... && go vet ./... && go test ./...`. Go 1.25.7. Config is env only (see README). Builder tests use `factorytest.Run` (or `Build`), which runs the real builder through the SDK in process and returns the plan, the progress and the result.
