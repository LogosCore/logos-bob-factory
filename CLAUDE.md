# CLAUDE.md

BOB (`github.com/logoscore/logos-bob-factory`): a bare Logos factory (the module type that builds minions). `cmd/bob-factory/main.go` runs factory-core's `factory.Run` as module_name `bob`, with its own management and the live log tail (module-core `logging.New` teed into a `logstream.Hub`). `build.go` holds its build schema (`schema_version` "3", version 3, one target: `linux-elf` on `linux/amd64` / `linux/386`, a compiled binary that prints the dummy minion's JSON description; one field of each build field type; HTTP (connection schema v3) with connection parameters per kind: `reverse-call` `method` and `path_prefix`, `reverse-persistent` `path_prefix` only; commands of each kind: required, default, operator-picked), its plan (`Steps`: check the badge when there is one, compile, upload), with the compiler's stdout and stderr streamed into the build log (`lineLog`), and the builder, which reports those steps, compiles the minion (`minion/`, a Go module of its own, copied per build with the description written in as `minion.json`; `compile.go`) for the build's platform, and uploads the binary as `bob-<id8>.bin`. Run, the minion stages with core through its first http connection, says hello (a session opens), then checks in with `get_tasks` (max 1) every `checkin_interval` ± `checkin_jitter` % of its connection until stopped, and logs each step. It keeps its session through failed check-ins and starts over from the stage only on a sealed `session_closed`, after 24 hours of failures (`backstop`), or when the stage or hello fails. BOB declares `persisted_sessions`: a build with a `session_id` writes it into the description, and the minion claims it in its hello until a `session_replaced` (then it stops claiming) (`minion/main.go`; `describe` prints the description); it vendors the protocol package, the CBOR library and coder/websocket (`minion/vendor`, built with `-mod=vendor`, no network). Commands and their params are numbered (`op`, `num`): tasks name them by number, so the minion dispatches on the constants in `minion/ops.go` and carries no command names; `cmd/bob-factory/ops_test.go` checks the schema and `ops.go` agree. A connection of kind `reverse-persistent` (BOB declares `reverse-call` first, then it) keeps a WebSocket to the HTTP channel (`minion/ws.go`): every exchange goes over it, core pushes tasks and cancels within the minion's `get_tasks` allowance, the minion checks in at once after hello (and after each reconnect) and then not on a schedule while the WebSocket stays open (only what it has to send, a pushed task's ack at once, and a failed exchange's retry after the reconnect back-off, 1s doubling up to `ws_reconnect_backoff`; it pings the channel every 30s, `wsPing`, to find a dead link), and a WebSocket that closes reopens after 1s doubling up to `ws_reconnect_backoff`. The HTTP channel closes the WebSocket when its socket to core closes, which is what makes the schedule unnecessary. The minion holds all of the build's connections (`minion/conns.go`, `transport`) and uses one at a time, the first it can use (an http one of a reverse kind) at start; its hello says which (`conn`, its place from 1). The `connect` command (op 12, action `switch_connection`: `conn`, and `for`, default `0s`) asks the session loop to move: it checks in through the new connection with a `conn_update` and the check-in's items, and moves only if that answers (the task fails, staying put, otherwise); with `for` it moves back when the time is up ("back after …"). The session, keys and schedule stay the same across moves. `stage_test.go` runs a compiled minion against a fake channel and core (stage, hello, a check-in that gets a 404 and keeps the session, one that gets `session_closed` and stages again, then kills it; and one built with a persisted session claiming it, then not after `session_replaced`). The image keeps the Go toolchain (`golang:1.25-alpine`) and the sources in `/app/minion` (`MINION_SRC`); the compile tests use `../../minion` and need `go` on `PATH`. `go test ./...` at the root does not cover `minion/`: vet it in its own directory. `icon.go` holds its icons (constant SVGs sent at registration: `icon`, the lit skin, for dark themes, and `iconLight`, the outline, lines and shading, for light ones; a test checks both against `protocol.ValidateIcon`). `management.go` is BOB's own manifest: `fail_builds` and `log_level` (live), and the `say_hello` action; factory-core adds the builds section (`max_concurrent_builds`, `drain`/`resume`, build counters) next to it, so BOB's manifest cannot use those keys.

Factory plumbing (build requests, progress, results, files, artifacts) stays in `logos-golang-factory-core`; module plumbing in `logos-golang-module-core`. BOB only declares what it builds and builds it.

Build and test: `go build ./... && go vet ./... && go test ./...`. Go 1.25.7. Config is env only (see README). Builder tests use `factorytest.Run` (or `Build`), which runs the real builder through the SDK in process and returns the plan, the progress and the result.
