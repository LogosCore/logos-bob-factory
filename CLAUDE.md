# CLAUDE.md

BOB (`github.com/logoscore/logos-bob-factory`): a bare Logos factory (the module type that builds minions). `cmd/bob-factory/main.go` runs factory-core's `factory.Run` as module_name `bob`, with its own management and the live log tail (module-core `logging.New` teed into a `logstream.Hub`). `build.go` holds its build schema (`schema_version` "3", version 6, two targets: `linux-elf` on `linux/amd64` / `linux/386` / `linux/arm64` / `linux/arm` (its own field `goarm`, num 5, for `linux/arm` alone: `platforms`; `compile` sets `GOARM` from it, 7 when none, `goarmOf`), and `windows-exe` on `windows/amd64` / `windows/386` / `windows/arm64`, the same minion compiled for each, which prints its config when run with `describe`; `minion_config`: the minions read core's minion config (docs: minion-build, The minion config) by numbers alone, so the channels (`http` 1, `tcp` 2), the build fields (`greeting` 1, `kill_date` 2, `punches` 3, `badge` 4: a file, numbered as every field must be, never in the config, `goarm` 5: the compiler's, which the minion never reads) and the connection parameters (`method` 1, `path_prefix` 2) are numbered, the minion's constants for them and for the channels' own fields in `minion/fields.go`, checked by `cmd/bob-factory/fields_test.go` against the schema and `channels_test.go` (the HTTP and TCP channels' numbered schemas, with which the tests make configs as core does: `withConfig`); one field of each build field type; HTTP (connection schema v3) with connection parameters per kind: `reverse-call` `method` and `path_prefix`, `reverse-persistent` `path_prefix` only; commands of each kind: required, default, operator-picked), its plan (`Steps`: check the badge when there is one, compile, upload), with the compiler's stdout and stderr streamed into the build log (`lineLog`), and the builder, which reports those steps, compiles the minion (`minion/`, a Go module of its own, copied per build with core's minion config written in as `minion.cfg`, the bytes as they came; `compile.go`) for the build's platform (`compiledTargets`), and uploads the binary as `bob-<id8>.bin` (`application/x-executable`) or `bob-<id8>.exe` (`application/vnd.microsoft.portable-executable`) (`artifactKinds`). What differs by OS lives in files of their own, Unix and Windows: the shell (`shell_unix.go`: `/bin/sh -c` in its own process group; `shell_windows.go`: `cmd.exe /d /s /c` as typed, `taskkill /T /F` on a cancel), the machine id (`machine_unix.go`: a container's id, the machine-id; `machine_windows.go`: the SMBIOS UUID via `GetSystemFirmwareTable`, the registry's `MachineGuid`), the hello's integrity and domain (`host_unix.go`, `host_windows.go`: the token's mandatory label, `NetGetJoinInformation`), listings' hidden files (the hidden attribute on Windows), and the `volumes` command (op 13, action `list_volumes`, result `volumes`, picked by default: `volumes_linux.go` reads `/proc/self/mountinfo`, `volumes_windows.go` the drives A: to Z:; `volumes.go` sends them in parts of half a message each); only `syscall`, no new modules. What is plain code (`smbios.go`, `integrity.go`, `shell.go`'s `cmdLine`) is tested on any host (`windows_test.go`); nothing here runs Windows, so vet and lint the minion with `GOOS=windows` (amd64 and 386) too. The image warms the standard library for `linux/amd64`, `linux/386` and `windows/amd64`. Run, the minion stages with core through its first http connection, says hello (a session opens, the hello saying its `max_tasks`), then checks in every `checkin_interval` ± `checkin_jitter` % of its connection until stopped, and logs each step. BOB declares `max_tasks`: the build's limit (default 5, the config's) is how many tasks the minion runs at once, each in a goroutine of its own; its `get_tasks` asks for the room the limit leaves through a call (none when full) and for the limit itself on a persistent connection (a standing allowance); core's `max_tasks` item (17) changes it live and the minion says it back in its next message (`minion/tasks.go`); `exit` cancels the tasks running beside it and waits for their ends (`exitWait`, 10s) before its own. Feedback (protocol item 18, `minion/feedback.go`): a process-wide queue anything reports into (`report`), at most 100 unsent (then a `feedback_dropped` warning), the same one folded into a count, sent first in each message (half its room at most) and at once (the session's runner's nudge); a failed message sends it again. It reports check-ins failing two or more in a row once one works (`failStreak`, `checkin_failed`), the WebSocket closing when the minion did not close it (`ws_closed`), the TCP listener refusing past `max_connections` (`tcp_refused`), a persisted session not given (`session_not_claimed`), and a command that panics (`task_panic`: recovered, the task fails; tests swap commands through `runner.exec`). The `feedback` command (op 14: `level` warning or error, `message`) sends the operator's words. It keeps its session through failed check-ins and starts over from the stage only on a sealed `session_closed`, after 24 hours of failures (`backstop`), or when the stage or hello fails. BOB declares `persisted_sessions`: a build with a `session_id` has it in its config, and the minion claims it in its hello until a `session_replaced` (then it stops claiming) (`minion/main.go`); its modules (the protocol package, the CBOR library, coder/websocket) are not vendored: the compile uses `-mod=readonly` and the module cache, which the image warms (`go mod download` on a copy without `replace` lines), and fetches what is missing through `GOPROXY` as BOB's environment sets it (a mirror where there is no internet), checked by `minion/go.sum`. While the minion needs an unreleased protocol, `minion/go.mod` has a `replace` to the checkout's absolute path (a build copies the minion to a scratch folder, so a relative one would not resolve), and the git-excluded `docker-compose.override.yml` mounts the checkout at that path; drop it at release. Commands and their params are numbered (`op`, `num`): tasks name them by number, so the minion dispatches on the constants in `minion/ops.go` and carries no command names; `cmd/bob-factory/ops_test.go` checks the schema and `ops.go` agree. A connection of kind `reverse-persistent` (BOB declares `reverse-call` first, then it) keeps a WebSocket to the HTTP channel (`minion/ws.go`): every exchange goes over it, core pushes tasks and cancels within the minion's `get_tasks` allowance, the minion checks in at once after hello (and after each reconnect) and then not on a schedule while the WebSocket stays open (only what it has to send, a pushed task's ack at once, and a failed exchange's retry after the reconnect back-off, 1s doubling up to `ws_reconnect_backoff`; it pings the channel every 30s, `wsPing`, to find a dead link), and a WebSocket that closes reopens after 1s doubling up to `ws_reconnect_backoff`. The HTTP channel closes the WebSocket when its socket to core closes, which is what makes the schedule unnecessary. A connection through the TCP channel (`tcp`, kind `bind-persistent`) makes the minion listen instead (`minion/tcp.go`, `tcpLink`: `listen_port`, `listen_address`, `max_connections`, `keepalive`): the channel dials it when core opens the target's connection, frames are `[len u32 BE][id 16][sealed]`, the newest connection in is the one used, an exchange waits for a dial while none is in. It is the one in use at start only when it comes first in the build; otherwise `switch` to it opens its port (`transport.listen`) and the session goes on through the connection in use, the task saying it listens (an early part: core's cue to dial the session's target), and the move goes through core's dial once it comes (`awaitDial` in `main.go`); no dial in `listenWait` (10m) closes the port and fails the switch. Moving off it is a switch like any (the port closes: `tcpLink.close` stops listening, also when a session ends), and a `for` back onto it waits for a dial the same way. Compression (`minion/packing.go`; docs: wire format, Compression): BOB declares `compression` `["deflate"]`; the config's compression (none when the operator turned it off) sets `packs` in `run`. `seal` packs each item where it pays (`protocol.Pack`); `readCore`, the one reader of core's messages (the sync call's reply, `openReply`, the WebSocket's, the TCP links'), takes packed items in place whatever the build, and the runner answers one that did not unpack by its index (`packedErr`: `too_large` or `bad_message`). Messages keep within the connection by their items' own sizes: packing only shrinks them. The WebSocket, the listener and the TCP channel's reverse-persistent connection (`tcpDialLink`) share the `persistentLink` interface (`transport.link`). What core pushes over one queues without a limit (`minion/pushqueue.go`, `pushQueue`; core bounds it: the task allowance, each stream's window): the connection's reader never waits on the loop, which takes all that is queued at once, when idle and before each exchange (a 16-message buffer once deadlocked a session behind 3 delegates: a reply sat behind a push the reader could not hand over, and the peer's close went unseen). A connection that fails a write, or gives no reply within the request timeout, is dropped (closed, the session told it is lost), so the next exchange dials, opens or waits for a dial again (`pushqueue_test.go`). BOB declares `failover`: the build's failover policy comes in the config (`protocol.DefaultMinionFailover` when it has none), and `minion/failover.go` acts on it in the session loop: `fail_after` failed exchanges in a row (a connection's own `fail_after` overrides it) over at least `fail_for` move the minion to the next connection it may use (`auto`), round the list with `wrap`; a round back to the connection in use pauses `cycle_pause` there; away from its first connection by failover it tries that one again after `failback_after`; an operator's switch resets it. Moves go through `move`, as a switch's, with a `conn_update` saying why. Failover passes listening connections by. Tunnels (protocol items 21 to 28, `minion/tunnel.go`): the `tunnel` command (op 15, action `tunnel`, operator-picked: `timeout`, `max_streams`; `opens` tcp, udp, unix, pipe, source, tls, process, accept and icmp, the `linux-elf` target narrowing it to all but pipes) and the `reverse_tunnel` command (op 17, action `reverse_tunnel`: `bind` (`0.0.0.0`), `listen`, `udp` (false), `timeout`, `max_streams`; `opens` tcp and udp); op 16 (a port forward's before the fronts were core's) is never used again. Core adds its own params to both (a tunnel's `front` and `port`, `host`, `to`, `stop_idle` (1h for a tunnel, never for a reverse one), `cap` and the rest: `protocol.TunnelCoreParams`, unnumbered, never sent; a factory declares none of them; a tunnel's each apply by its front, `when`), so what is in front (SOCKS, HTTP, a forward, a terminal; a reverse tunnel's forward, its one front since reverse SOCKS was dropped in wave 3.2, which no param names since 3.3) is core's alone and the minion's side is the same for each. BOB's own `timeout` and `max_streams` are `advanced` (the form's More options), and the tunnel's `timeout` applies with any front but `terminal` (its `when` names core's `front`: a terminal connects to nothing; `vpn` among them). Pings (the VPN front's, an open of kind icmp: `minion/tunnel_icmp.go`): a stream whose datagrams are echo requests to any address, sent by the host's pinger (`icmp_unix.go`: an unprivileged ICMP socket by `syscall.Socket` and `net.FilePacketConn`, the kernel's identifier, no errors delivered; else a raw one as root, the minion's identifier picking its echoes and errors; IPv6's opened at its first echo; `icmp_windows.go`: `IcmpSendEcho` from iphlpapi, any user, IPv4 alone, 64 at once; none: denied, `icmp_other.go`), what answers queued as datagrams as a UDP association's are (`tunnel_icmp_test.go` pings 127.0.0.1). Timing follows the link (change 9, `minion/rtt.go`): a resend waits the session's measured round trip and four times its spread (RFC 6298, Karn's rule), `tunnelResend` at least, a minute at most; a stream's window, the room it gives core, doubles while core fills it and the host keeps up, to 4 MiB (32 MiB over a tunnel), and it reads up to 4 MiB of a host ahead of core's ack. An open is read strictly (`protocol.ReadTunnel`): one with a key the minion does not know, or that does not read though its task and stream do, is answered `tunnel_reply` result 7 unsupported and connects nowhere (`tunnel_test.go` TestTunnelUnsupported); bytes core sends with an open, before its reply, are written once connected. The same tunnel runner (`tunnelCmd`, `runner.runTunnel`; `tunnelArgs` reads each one's limits by its own numbers), whose tasks hold no place in its max tasks (`roomLocked` leaves them out), each make its tunnel as the task is taken (before its ack goes: core opens streams only once it has it) and runs until core cancels it (then its streams close and it ends ok, as with the session's end). A reverse forward (`runner.reverse`) listens as its task starts (a listener that does not open, or fails, ends the task failed, saying why), says where in a `tunnel_listen` (item 27), and opens a stream for each connection that comes, numbered by the minion from 1: its `tunnel` item names who connected, and the connection waits unread for core's `tunnel_reply` (open: relayed as any stream; refused, or none within `timeout` and `reverseSlack` (30s) more: reset, core told with a close); the `tunnel` again every `tunnelResend` while core has not answered; past `max_streams` a connection is reset at once, and core's own `tunnel` for the task gets a close, task ended (`tunnel_reverse_test.go`). Each `tunnel` item core sends is a TCP connect from the host within `timeout` (`openConn`; `dialResult` says why one failed, by the host's errors: `tunnel_unix.go`, `tunnel_windows.go`'s Winsock codes, a path not there `not_found`, access refused `denied`); its reply says the socket's address. One with a `kind` connects to its `path` instead: a unix socket, or a named pipe (`pipe_windows.go`: an overlapped `CreateFile`, retried every 50 ms while the pipe is busy, then `os.NewFile`; a remote one over SMB as the minion's user; off Windows unsupported, `pipe_other.go`). A TCP one's `source` is the local address it goes from, and its `tls` speaks TLS to the destination, no certificate checked (`tunnel_kinds_test.go`). Each stream mirrors core's: offsets each way, the eof one place past the bytes, a 256 KiB window the minion gives (growing, `rtt.go`), at most 4 MiB read ahead of core's ack, unacked data sent again from the ack after the round trip (`tunnelResend`, 5s, at least), a window shut that long probed with one byte, core's data that comes ahead kept until the gap fills; a UDP association (a tunnel item that says udp) is a UDP socket of the minion's on every interface (`minion/tunnel_udp.go`): core's `tunnel_datagram`s go out of it (a name resolved apart, cached a minute), what comes back goes to core with its source, at most 256 KiB queued (then dropped, as UDP is), each `seq` taken once (the latest and 64 before it); in a message, closes, replies, acks, then data a stream's item in turn (192 items at most, half the room while a file goes). `pending` counts tunnel items, so the minion checks in at once with them; core's `poll` of 0 means at once (`polled`), and a resend due wakes the loop even over a persistent connection (`pollEvery`). Core's items the minion does not take get `unknown_item` (`resume` among them: it keeps its own state); a `rehello` gets a `hello` in the next message, through the connection in use; a `reack` (item 19: which tasks it still has, asked after a claim and over each new listening connection) gets an `ack` naming those it has (running, or ended with an end not yet delivered) and `unknown_task` for each other (`runner.reack`). A held stream is not polled on a guess: core's `poll` item (in a sync-call reply, while the stream's downloader or uploader is there) says how soon to check in, for the next wait only; over a WebSocket or a TCP connection core pushes instead. Each message keeps within the connection in use's `max_message` (`MinionConnection.MessageLimit`, set into the runner each loop): output, data, chunks and listing pieces take two thirds of it at most (512 KiB over the protocol's limit), and a listing piece half of that. The minion holds all of the build's connections (`minion/conns.go`, `transport`) and uses one at a time, the first it can use (an http one of a reverse kind) at start; its hello says which (`conn`, its place from 1). The `switch` command (op 12, action `switch_connection`: `conn`, and `for`, default `0s`) asks the session loop to move: it checks in through the new connection with a `conn_update` and the check-in's items, and moves only if that answers (the task fails, staying put, otherwise); with `for` it moves back when the time is up ("back after …"). The session, keys and schedule stay the same across moves. `stage_test.go` runs a compiled minion against a fake channel and core (stage, hello, a check-in that gets a 404 and keeps the session, one that gets `session_closed` and stages again, then kills it; and one built with a persisted session claiming it, then not after `session_replaced`). The image keeps the Go toolchain (`golang:1.25-alpine`) and the sources in `/app/minion` (`MINION_SRC`); the compile tests use `../../minion` and need `go` on `PATH`. `go test ./...` at the root does not cover `minion/`: vet it in its own directory. `icon.go` holds its icons (constant SVGs sent at registration: `icon`, the lit skin, for dark themes, and `iconLight`, the outline, lines and shading, for light ones; a test checks both against `protocol.ValidateIcon`). `management.go` is BOB's own manifest: `fail_builds` and `log_level` (live), and the `say_hello` action; factory-core adds the builds section (`max_concurrent_builds`, `drain`/`resume`, build counters) next to it, so BOB's manifest cannot use those keys. With `udp` it listens for datagrams instead (`tunnel_udp.go`: `listenUDP`, `sources`): a stream for each source address, opened with a UDP `tunnel` naming it, its datagrams held (up to `udpQueue`) until core answers, then `tunnel_datagram`s with that address; core's go to the source from the socket, whatever they name; a stream with no datagram either way for `udpIdle` (`protocol.TunnelUDPIdle`, shorter in tests) ends with a done close (`endIdle`), and a source past `max_streams` has its datagrams dropped.

Processes and accepts (core's terminal front and SOCKS5 BIND; `minion/proc.go`, `tunnel_ctl.go`): an open of kind process runs its program (none: `$SHELL` or `/bin/sh`, `%ComSpec%`) with its args, in a terminal of its rows and cols (`proc_linux.go`: a PTY from `/dev/ptmx` by ioctl, syscall alone, the process its session's leader, a signal to the terminal's foreground group; `proc_windows.go`: a ConPTY by `CreatePseudoConsole` and `CreateProcessW` with an attribute list, an interrupt typed as Ctrl-C, terminate and kill `taskkill /T`), or on pipes with no size or no terminal to give (no `/dev/pts`, a Windows before 1809), its reply's `terminal` saying which; stderr merged either way. Its output's end waits for its exit, which goes to core as a `tunnel_ctl` before the eof (128 and the signal's number on Unix); the stream's close kills it. An accept listens where the open says for one connection (`acceptWait`, `protocol.TunnelAcceptWait`), its reply where, a ctl who came, then the stream is theirs; an address taken is `in_use`. Ctls are numbered each way, sent again from core's ack (`tunnel_ack`'s `ctl`) after `tunnelResend`, taken once in order, and a stream ends done only once its own are acked. `tunnel_proc_test.go` runs real processes (pipes, a PTY when the host has one, a signal, a lost ack) and accepts. Nothing here runs a ConPTY: the user tests Windows by hand.

Delegation (protocol item 29, `minion/delegate.go`, docs: contracts/minion-messages/delegation): the `delegate` command (op 18, action `delegate`, operator-picked, `serves` the TCP channel's `bind-persistent` kind v1, `kinds` reverse-call, reverse-persistent and bind-persistent) makes the minion an instance of that kind while its task runs (made as the task is taken, like a tunnel's; it holds no max-tasks place, `holdsNoSlot`). Core's `open` steps name a target's values: it dials `host` and `port` (the `listen_port` when none) within `connect_timeout` and the open's deadline, never through a `proxy` (failure `other`), answers each open once by its number (again when it comes again), then relays `[len][id][sealed]` frames (tcp.go's framing) both ways: the dialed minion's as `frame` items numbered by `seq`, cut in pieces where the message has no room (`delegates.items`, `cutDelegate`); core's joined from pieces (`protocol.DelegateJoiner`) and written by a writer per connection (64 queued, then dropped). A connection that ends says `close` 1; core's close is answered with one; a frame for a connection it lacks gets `close` 2, an item of a task it does not run `close` 3. The task's cancel closes its connections and ends it ok. `delegate_test.go` dials a real listener. The `reverse_delegate` command (op 19, `minion/delegate_reverse.go`: `bind`, `listen` required (an operator starts it: no default needed), `kind` reverse-persistent or reverse-call, `max_connections` 16; serves `tcp` v1 reverse-call and reverse-persistent) listens until cancelled (a listen that fails ends it failed): each minion that dials it is a connection numbered by the minion (its first frame names `serve` 1 and the peer), or, for reverse-call, an exchange: a `sync` item, core's `reply` written back (the id alone for 204; none for a refusal or no reply in `reverseCallWait`, 35s). The minion speaks the TCP channel's reverse kinds itself too (`minion/tcp_reverse.go`): `reverse-persistent` a `tcpDialLink` kept open like the WebSocket (`dialLink` picks it; `reconnect_backoff`), `reverse-call` `tcpCall` per exchange (`readTCPReply` takes an empty reply). `tcp_reverse_test.go` covers both kinds against a fake channel and the reverse delegate against real dialers.

Error codes (`error_codes` in `build.go`; docs: minion-build, Minion error codes): what the minion's exit codes mean, shown by core on BOB's page and on each build's Overview and used for nothing else: 1 could not start (any other reason; the log says which), 2 crashed (Go's own: a panic no task recovered, a fatal error of the runtime), 3 its config does not read, 4 built without core's keys, 5 no connection it can use. `minion/exits.go` holds them as constants alone (no imports: `cmd/bob-factory/exits_test.go` reads them from source and checks them against the schema, and runs a minion whose config does not read, expecting 3); `readDescription` and `run` give their errors a code (`withCode`, `main.go`) and `main` exits with it (`exitCode`: 1 for an error without one). A code once given keeps its meaning: minions already built exit with it. BOB declares `error_codes_per_build` (version 5): core draws each build's own exit codes (3 to 255) for 3, 4 and 5; 1 and 2 are `fixed` (Go's, which the runtime and libraries exit with too). The request carries them (`req.ErrorCodes`); `exitCodes` and `bakeExitCodes` (`compile.go`) write them into the build's scratch copy of `exits.go` before `go build`, each constant swapped by its declared value as it stood (codes that trade places never chain), and the build log names them; the sources are never written. `exits_test.go` covers the bake and a minion exiting with its build's code; `bob_test.go` sends a request with codes through factory-core.

Factory plumbing (build requests, progress, results, files, artifacts) stays in `logos-golang-factory-core`; module plumbing in `logos-golang-module-core`. BOB only declares what it builds and builds it.

Build and test: `go build ./... && go vet ./... && go test ./...`. Go 1.25.7. Config is env only (see README). Builder tests use `factorytest.Run` (or `Build`), which runs the real builder through the SDK in process and returns the plan, the progress and the result.
